We built [Pandemonium](/projects/pandemonium/), our N64brew game-jam boss battle, with very little time for optimization. We didn’t get to check every texture’s size or format, and the room wasn’t textured as nicely as we wanted. There was lots of overdraw. Z fighting on the floor. Assets didn't make it into the final build. Usual game-jam chaos.

Revisiting the scene gave us time to improve the artwork and look at what each surface actually needed. The stone floor went from I8 to I4: 4kb down to 2kb, still at 64 × 64. The mesh still supplies its color.

All Pandemonium textures were made by my teammate [BoxingBruin](https://github.com/Boxingbruin).

## Small textures, tight budget

A texel (texture element) is one pixel in a texture, so a 64 × 64 texture contains 4,096 texels.

The N64’s graphics hardware has 4kb of texture memory, called TMEM. That is space for textures being used while drawing, rather than a limit on all the artwork in a game. The RDP can only sample texels already loaded there, so textures that exceed that space must be drawn in smaller sections, with new texture data loaded between draws.

<FormatFamilies />

Fewer bits can leave room for more texels, at the cost of brightness levels, colors, or transparency precision.

| Format | Bits / texel | What it stores |
| :--- | ---: | :--- |
| I4 | 4 | 16 brightness levels |
| I8 | 8 | 256 brightness levels |
| IA4 | 4 | 3 intensity bits + 1 alpha bit |
| IA8 | 8 | 4 intensity bits + 4 alpha bits |
| IA16 | 16 | 8 intensity bits + 8 alpha bits |
| CI4 | 4 | An index into a 16-color palette |
| CI8 | 8 | An index into a 256-color palette |
| RGBA16 | 16 | 5 bits per RGB channel + 1 alpha bit |
| RGBA32 | 32 | 8 bits each for red, green, blue, and alpha |
| YUV16 | 16 | Brightness per texel, with U and V shared by a horizontal pair. No alpha |

These layouts follow [libdragon’s texture-format definitions](https://github.com/n64brew/libdragon/blob/f26e1c16145e4d6ad7e391e1306513d684083c02/include/surface.h#L105-L118).

## Texture dimensions

BoxingBruin pointed out two rules about width and height that are easy to miss.

To repeat or mirror a texture along an axis, that dimension must be a power of two: 16, 32, 64, and so on. [libdragon checks this](https://github.com/n64brew/libdragon/blob/f26e1c16145e4d6ad7e391e1306513d684083c02/src/rdpq/rdpq_tex.c#L58-L70) separately for each axis.

Any size that fits in TMEM can still be drawn once. Keep the width to these multiples so each row fills whole 64-bit rows of TMEM:

| Formats | Width is a multiple of |
| :--- | ---: |
| I4, IA4, CI4 | 16 |
| I8, IA8, CI8 | 8 |
| IA16, RGBA16 | 4 |
| RGBA32 | 4 |

RGBA32 is split across both halves of TMEM, so it lines up at 4 texels rather than 2. [libdragon pads rows](https://github.com/n64brew/libdragon/blob/f26e1c16145e4d6ad7e391e1306513d684083c02/src/rdpq/rdpq_tex.c#L133-L137) that don’t line up, which wastes TMEM.

A 40 × 48 RGBA16 texture is 3,840b. Its rows line up and it fits, but it can’t repeat, because neither 40 nor 48 is a power of two. As I4, each 40-texel row is 20b, padded to 24b.

The room has examples. The carpet border is 16 × 64 CI8, and its material mirrors it horizontally, which the 16-texel width allows. The door crests and window frames are 48 × 80 IA8, and the column transition is 32 × 124 I4. Their rows line up, and none of them can repeat vertically.

## Which format would I use?

I’d start with what the surface needs. Each pair below uses the same source, so you can see what changes when you spend more memory.

<FormatChoiceGuide />

For colored cutouts, RGBA16 or CI with an RGBA16 palette gives you on/off alpha. YUV16 is a separate case for video frames or photographs: it keeps brightness detail but shares color between neighboring texels, and has no alpha. It uses [libdragon’s dedicated YUV conversion mode](https://github.com/n64brew/libdragon/blob/f26e1c16145e4d6ad7e391e1306513d684083c02/include/rdpq_mode.h#L346-L362).

For surfaces that recede into the distance, [mipmaps](https://github.com/n64brew/libdragon/blob/f26e1c16145e4d6ad7e391e1306513d684083c02/include/rdpq_mode.h#L830-L856) can reduce shimmering. They add storage, so budget for the levels that need to be loaded together.

## Vertex colors

If you can get away with a simple color then this is definitely the way to go. A grayscale stone texture can still produce a colored floor. The texture supplies fine detail. Colors stored at the mesh’s vertices supply broader variation. The renderer blends those corner colors across the entire triangle, then multiplies the texture by that color:

```text
surface RGB = texture intensity × interpolated vertex RGB
```

<VertexColorDemo />

For 2kb of raw texels, RGBA16 gives you 32 × 32 pixels, while I4 gives you 64 × 64: four times as many texels. Putting broad color changes in the vertices can preserve a larger grid for surface detail.

Vertex colors do not increase the screen resolution or add texture pixels by themselves. Their gradients follow the mesh, and vertex data also costs memory. The original floor already used this technique, and the revision keeps it.

## How the color combiner builds the material

The texture format tells us what is stored. The color combiner decides how those samples mix with the other inputs. Vertex colors only affect the result if the material’s formula uses them.

Each cycle runs this formula separately for RGB and alpha:

```text
(A − B) × C + D
```

The letters are input slots, like the fields in Fast64. Some of the inputs you can choose are:

- **Texture 0 / 1:** Color and alpha sampled from the first or second texture.
- **Shade:** Vertex color or lighting, blended across the triangle.
- **Primitive:** A fixed color set by the material or drawing code. Here it tints the columns.
- **Environment:** A second fixed color the formula can use.

The available inputs depend on the slot. See [libdragon’s formula and input definitions](https://github.com/n64brew/libdragon/blob/f26e1c16145e4d6ad7e391e1306513d684083c02/include/rdpq_macros.h#L310-L410).

<ColorCombinerDemo />

In a two-cycle material, Combined is the first cycle’s output, used as an input to the second. See [libdragon’s documentation for the second cycle](https://github.com/n64brew/libdragon/blob/f26e1c16145e4d6ad7e391e1306513d684083c02/include/rdpq_macros.h#L474-L495).

The two-texture blend preset uses

```c
(Texture 1 − Texture 0) × amount + Texture 0
```

This is a lerp: amount 0 gives Texture 0, amount 1 gives Texture 1. It uses primitive alpha as the mix amount, then applies shade in cycle 2. Both textures must fit in TMEM together. These two 32 × 32 I4 patches use 1kb in total.

On an N64 model, the UVs select the texture samples and the vertex data supplies shade. Fast64 stores the combiner choices in the exported material, which the model pipeline must apply when drawing. Changing the PNG alone cannot change that formula. For the column settings, the equivalent libdragon configuration is:

```c
rdpq_mode_combiner(RDPQ_COMBINER2(
    (TEX0, 0, SHADE, 0),       (0, 0, 0, 1),
    (COMBINED, 0, PRIM, 0),   (0, 0, 0, COMBINED)
));
rdpq_set_prim_color(RGBA32(255, 255, 255, 255));
```

The combiner is only part of the material. Lighting supplies shade before this step. The later blender handles mixing with the framebuffer. Alpha testing can discard cutout pixels. Standard fog also uses the blender, often borrowing shade alpha for depth, so it needs care alongside custom alpha formulas. See [libdragon’s notes on fog and the combiner](https://github.com/n64brew/libdragon/blob/f26e1c16145e4d6ad7e391e1306513d684083c02/include/rdpq_mode.h#L413-L467).

## What changed in the room?

The floor’s artwork also changed, so the before-and-after images show more than a format conversion.

| Surface | Original → updated | Outcome |
| :--- | :--- | :--- |
| Stone floor | 64 × 64 I8 → I4 | 4kb → 2kb of texels |
| Carpet border | 16 × 64 CI8 in both | Same 1kb base cost, with revised artwork and added mipmaps |
| Banner layers | Separate I4 background and IA4 ornament in the local version | Different jobs for brightness and transparency |

The carpet still uses CI8. Its mipmaps actually add memory, but help stop the fine pattern shimmering in the distance. The banner layers show another tradeoff, spending bits on independent alpha where a decorative cutout needs it.

## Conclusion

The floor saves 2kb. The updated room still has more texture data and geometry overall:

| Room assets | Original | Updated |
| :--- | ---: | ---: |
| Model files | 10 | 12 |
| Triangles in those models | 1,316 | 2,321 |
| Material slots across models | 32 | 72 |
| Unique embedded textures | 18 | 51 |
| Estimated packed embedded texels | 69kb | 131.56kb |

Asset totals include room effects. Texel estimates exclude palettes, external mipmaps, padding, and headers.

During the jam, getting the game finished took priority. Coming back gave us time to revisit choices like the floor’s format and bring the stonework and banners closer to how we wanted them to look.

I hope this little deep dive into texture formats and the color combiner helps understand some of the finer details of Nintendo64 graphics.
